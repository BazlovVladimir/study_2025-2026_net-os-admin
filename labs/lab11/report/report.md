# Цель работы

Приобретение практических навыков по настройке удалённого доступа к серверу с помощью SSH.

# Выполнение

## Запрет удалённого доступа по SSH для пользователя root

1. На сервере был установлен пароль пользователя **root**.

2. Во втором терминале был запущен мониторинг системных событий.

3. С клиента выполнена попытка подключения по SSH под пользователем **root**.  
   Аутентификация завершается неудачей, несмотря на ввод пароля.  
   Сервер фиксирует ошибки проверки пароля, соединение отклонено.

   ![Неуспешная попытка входа под root](Screenshot_1.png){ #fig:001 width=80% }

   На сервере журнал фиксирует сообщения о неудачных попытках входа.

   ![Журнал: ошибки аутентификации root](Screenshot_2.png){ #fig:002 width=80% }

4. В файл `/etc/ssh/sshd_config` внесено изменение:  
   `PermitRootLogin no` — удалённый вход root запрещён.

   ![Установка PermitRootLogin no](Screenshot_3.png){ #fig:003 width=80% }

5. Служба sshd была перезапущена.

6. Повторная попытка подключения под root:  
   сервер сразу отклоняет соединение — root входить больше не может.

   ![Отклонение входа root после запрета](Screenshot_4.png){ #fig:004 width=80% }

## Настройка дополнительных портов для удалённого доступа по SSH

1. В конфигурации SSH на сервере под строкой `Port` были добавлены две строки:  
   `Port 22`  
   `Port 2022`  
   Это позволяет sshd работать сразу на двух портах — стандартном и резервном.

2. После сохранения конфигурации sshd был перезапущен.

3. При просмотре расширенного статуса sshd система сообщает об ошибке:  
   процесс не смог привязаться к порту 2022.  
   В сообщениях указывается *Permission denied* — SELinux запрещает использование нового порта.

   ![Ошибка привязки к порту 2022](Screenshot_10.png){ #fig:010 width=80% }

   Таким образом, демон не может начать прослушивание порта 2022 из-за некорректной SELinux-метки.

4. На сервере была исправлена SELinux-метка порта 2022, назначив ему тип `ssh_port_t`.  
   Теперь SELinux разрешает sshd работать с этим портом.

5. В брандмауэр были добавлены правила, позволяющие входящие соединения на порт 2022 (временно и постоянно).

6. После повторного запуска sshd в расширенном статусе видно, что sshd успешно слушает оба порта — 22 и 2022.

   ![Успешный запуск sshd на двух портах](Screenshot_11.png){ #fig:011 width=80% }

7. С клиента выполнено подключение к серверу под пользователем **vabazlov** на стандартном порту.  
   Открывается оболочка пользователя, после чего выполнен переход в root через `sudo -i`.  
   Далее выполнен выход из сеанса.

8. Повторное подключение выполнено на порт 2022 с использованием параметра `-p2022`.  
   Подключение успешно: теперь SSH доступен через оба порта.

   ![Успешный вход через порт 2022](Screenshot_12.png){ #fig:012 width=80% }

## Настройка удалённого доступа по SSH по ключу

1. На сервере в файле `/etc/ssh/sshd_config` был включён параметр:  
   `PubkeyAuthentication yes`  
   Это разрешает аутентификацию по SSH-ключам.

   ![Включение PubkeyAuthentication](Screenshot_13.png){ #fig:013 width=80% }

2. Служба sshd была перезапущена для применения параметров.

3. На клиенте под пользователем **vabazlov** была создана пара SSH-ключей командой `ssh-keygen`.  
   Кодовая фраза не задавалась, использованы значения по умолчанию.

4. Закрытый ключ сохранён в `~/.ssh/id_rsa`, открытый — в `~/.ssh/id_rsa.pub`.

5. Открытый ключ был скопирован на сервер командой `ssh-copy-id`.  
   После ввода пароля ключ успешно добавлен в `~/.ssh/authorized_keys` пользователя на сервере.

   ![Копирование SSH-ключа на сервер](Screenshot_14.png){ #fig:014 width=80% }

6. Повторная попытка подключения по SSH прошла успешно — теперь вход осуществляется без пароля.  
   Это подтверждает корректную настройку аутентификации по ключу.

# Контрольные вопросы

1. **Вы хотите запретить удалённый доступ по SSH пользователю root и разрешить доступ пользователю alice. Как это сделать?**  
   В конфигурационном файле SSH `/etc/ssh/sshd_config` необходимо:  
   - запретить вход root, указав: `PermitRootLogin no`,  
   - разрешить вход только пользователю alice, установив: `AllowUsers alice`.  
   После изменения файла требуется перезапустить службу sshd.

2. **Как настроить удалённый доступ по SSH через несколько портов? Для чего это может потребоваться?**  
   В файле `/etc/ssh/sshd_config` добавляют несколько строк `Port`, например:  
   `Port 22` и `Port 2022`.  
   Это позволяет подключаться через разные порты.  
   Такая настройка полезна при изменении конфигурации или тестировании нового порта, сохраняя основной порт доступным как резервный.

3. **Какие параметры используются для создания туннеля SSH, когда команда ssh устанавливает фоновое соединение и не ожидает какой-либо конкретной команды?**  
   Используются параметры:  
   - `-f` — переводит ssh в фоновый режим после установления соединения,  
   - `-N` — не выполняет удалённые команды,  
   - `-L` — создаёт локальный туннель для переадресации порта.

4. **Как настроить локальную переадресацию с локального порта 5555 на порт 80 сервера server2.example.com?**  
   Для этого выполняют команду SSH с параметром локального туннеля:  
   `ssh -fNL 5555:server2.example.com:80 user@server2.example.com`  
   Теперь обращение к `localhost:5555` передаётся на порт 80 удалённого сервера.

5. **Как настроить SELinux, чтобы позволить SSH связываться с портом 2022?**  
   Необходимо назначить порту 2022 SELinux-метку типа `ssh_port_t`:  
   `semanage port -a -t ssh_port_t -p tcp 2022`.  
   Это разрешает sshd работать с данным портом.

6. **Как настроить межсетевой экран на сервере, чтобы разрешить входящие подключения по SSH через порт 2022?**  
   Требуется добавить соответствующее правило в firewall:  
   - временно: `firewall-cmd --add-port=2022/tcp`,  
   - постоянно: `firewall-cmd --add-port=2022/tcp --permanent`.  
   Затем необходимо выполнить `firewall-cmd --reload` или перезапустить службу, чтобы изменения вступили в силу.

# Заключение

В ходе выполнения работы были последовательно изучены и применены механизмы администрирования удалённого доступа по SSH. Настройка сервисов включала ограничение доступа для отдельных пользователей, добавление вспомогательных портов, корректировку правил SELinux и конфигурации межсетевого экрана. Полученные навыки позволили глубже понять принципы организации защищённого удалённого взаимодействия, а также сформировать универсальный подход к управлению SSH-сервисом в различных сценариях эксплуатации. Эти результаты создают основу для дальнейшей автоматизации и усложнения конфигураций, что будет востребовано в последующих лабораторных работах.
